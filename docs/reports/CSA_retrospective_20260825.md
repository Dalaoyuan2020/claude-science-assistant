# CSA v0.1.6–v0.1.7 开发复盘

日期：2026-08-25

范围：v0.1.6 结构减负（S0–S5）与 v0.1.7 出口自愈（T0–T6）

## 两轮分别解决了什么

v0.1.6 解决的是“明明服务能用，却被体检卡住”的问题。它把“能不能打开”“健康状况如何”“用户主动维修”拆成三条互不否决的通道，并把主按钮锁定为只看 Claude Science 是否运行、是否有旧 Windows Bridge 冲突。同时加入秒级 smoke，让开发不再靠反复制作正式安装包判断改动是否有效。

v0.1.7 解决的是“所有灯都绿，模型请求仍然 502”的问题。现场证明沙盒出口和 Bridge 出口是两条不同链路：Bridge 曾指向无人监听的 10808。新版本从真实用户请求路径检查出口，能发现可用候选，只修改 `outbound_proxy_url` 一个字段，失败时只回滚这个字段，并把“代理不可达”与“Key/账号认证失败”分开说明。真实验收完成 DeepSeek → OpenRouter → DeepSeek 的切换与恢复。

## 最有价值的三个改变

1. **把唯一的锁写成测试。** `allow_inputs_frozen` 和 `all_probes_red_button_still_open` 共同保证磁盘、p9、出口和版本检查再红，也不能把可用系统变成不可打开。
2. **用同一条产品路径做秒级验证。** `--smoke` 在约 6 秒内完成 required 4/4 检查，替代了一天五个正式 ZIP 的调试方式。
3. **从真实请求链路诊断并事务化修复。** 出口检查、候选证明、单字段写入、读回、真实验证与局部回滚形成一条可审计链；错误码能直接指出是连接层还是认证层。

## 最该早点做的三件事

1. **先画端到端链路再写探针。** 如果一开始就从用户的模型请求反查 Bridge `httpx` 配置，就不会花大量代码证明一条并不承载用户请求的沙盒链路。
2. **第一次复发时就拆结构并补反例。** v0.1.6 开工前最近 12 个提交全是 `fix:`，没有 `refactor:` 或 `test:`；补丁列车让同型问题反复出现。
3. **从第一天维护台账和快速入口。** 台账曾停在 v0.1.5，12 个修复没有上下文；没有 smoke 时又把 Release 包当调试器，放大了目录、版本和产物来源混乱。

结构正确性明显改善，但代码体积仍在增长。下一轮改界面时，首要约束不是再加能力，而是保持同一 DOM 能力集合、同一 ALLOW 锁和同一事务入口。

## 当前已知欠账

- **Provider 崩溃一致性**：Bridge 已提交、Windows settings 尚未提交之间仍缺绑定 revision 的跨进程 durable journal。后续需实现 `PREPARED / COMMIT_DECIDED` 与启动恢复；当前只能保证正常错误路径回滚，不能声称进程崩溃原子性。
- **单体文件继续偏大**：两轮后 `lib.rs` 与 `App.tsx` 仍分别增长 25.3% 和 33.6%。后续新增能力要先指定模块归属，避免继续把 command、DTO、事务和界面状态堆回两个中心文件。
- **发布与破坏性验收未完成**：正式 ZIP/SHA-256/包内 secret scan/双入口/并排升级，以及维护窗口中的停止、重启、旧 Bridge fixture、真实新增 Key、聚合整表提交，仍按 S5 标为待人工或发布阶段。
- **验收工具兼容债**：`verify-proxy.ps1` 仍不能识别合法的 aggregate-only 三路配置；真实 WSL 出口故障夹具也应拆出纯逻辑 CI fixture。
